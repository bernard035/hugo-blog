九月初我确认家里那台跑 Immich 和 Gitea 的服务器中了 xmrig，顺手清理干净，写了份事件报告，以为事情到此为止。上周做例行服务盘点，在 systemd 服务列表里看到一个从没见过的东西：一个叫 `am4hddh8` 的服务，描述写着 "System Management Daemon"，ExecStart 指向 `/usr/lib/.feca615165204348`——一个以点开头、后缀随机十六进制的隐藏文件，连 PID 文件都是 `/run/.23f61c72877d2f39` 这种随机名。正经软件不会这样给自己起名字。这篇文章把接下来发生的完整取证讲一遍，深入浅出，也算给自己留档。

先交代背景。这台机器在家宽 NAT 后面，没有公网 IP，所有服务通过 frp 转发出去，Gitea 就这么暴露在公网上。第一波入侵是教科书式的自动化机器人打法：Web 注册账号，其中一个邮箱后缀拿到管理员权限，建仓库，调 diffpatch API 往仓库里写 payload，最后落到 git 用户的 crontab 里，每五分钟拉起一次 xmrig 挖 Monero。整个过程持续了三十六天，直到我在排查别的 CPU 占用时撞见矿工进程。当时的处置很干净：删账号、删 crontab、删落盘的三个 payload 目录、全盘扫描确认没有其他 dropper。"全盘扫描确认干净"——记住这句话，它是这篇文章的伏笔。

那个可疑服务被我发现时是 enabled 状态，只是因为机器自八月底以来没重启过所以一直没被拉起。文件创建时间是九月四日下午四点半，比事件报告里记录的"二次部署"还早四个小时。也就是说，我上次清理的"干净"，漏掉了真正的重头戏。

把二进制拽下来分析，6.3MB 静态链接的 Rust 程序，musl 编译，剥了符号，内嵌 libbpf-rs 的八个 eBPF skeleton。到这一步基本可以确定这不是又一个 xmrig 变种——它压根不挖矿，它是一个 rootkit，一个完整的、配置驱动的 eBPF rootkit。八个模块值得逐个说：`hide_pid` 和 `hide_files` 在内核态拦截 getdents 和 proc 文件系统，让指定进程和文件从 `ps`、`ls` 里消失；`execve_replace` 更进一步，任意进程启动时直接改写它的 execve 参数，于是你在 `ps` 里看到的命令行可以是攻击者想让你看到的任何东西；`anti_ptrace` 拦截 PTRACE_ATTACH，反调试自保护；`ghost` 模块实现所谓"魔法路径"——一套只有知情者能访问的隐形文件系统，普通方式列不出来、打开不了，但知道路径的进程可以正常读写。最狠的是 file-read 模块：BPF 挂钩别的进程读文件的动作，然后通过 `/proc/<pid>/mem` 直接给对方进程的内存打补丁。意味着 `cat /etc/passwd` 看到的可以是被改过的内容，sshd 读配置时读到的也可以是假的——你在用户态做的所有检测，它都有机会在数据到达你眼睛之前改掉。

整个程序没有硬编码的 C2 地址、没有矿池、没有钱包，所有配置运行时通过 BPF map 注入，还带一个 `fetch_exec` 模块负责下载执行后续 payload。它不是一个变现工具，它是一块等待入住的地皮。

真正精彩的是时间线还原。journal 和 audit 日志把九月四日下午四点三十三分前后的每一秒都记了下来。16:30:11，攻击者账号发起一个 diffpatch 请求，往仓库的钩子文件里写补丁，这个请求持续了两百零三秒。16:33:23 开始，audit 日志连续出现一百四十四条 `MAC_IPSEC_EVENT op=SAD-add`——往内核 XFRM 安全关联数据库里添加条目，源和目的都是 127.0.0.1，SPI 从 0xdeadbe10 开始逐个递增。这里有两个信息量：第一，添加 XFRM SA 需要 CAP_NET_ADMIN 权限，普通 web 进程根本做不到；第二，0xdeadbeef 风格的魔数 SPI 是漏洞利用代码里标志性的"我在这里"记号。紧接着 16:33:30，内核日志记录 `su` 以 NULL argv 拉起了 `/bin/sh`——一个没有参数的 root shell，空 argv 是为了让 `ps` 里看不到它在干什么。16:33:33，这个 shell 执行了 drop_caches 清空页缓存，而 `printf '3' > /proc/sys/vm/drop_caches` 恰好是那个 rootkit 二进制 strings 里的原句，同一个工具链。16:33:34，二进制和 unit 文件落盘，两者创建时间相差三十一毫秒；同一秒，一个 `systemctl daemon-reload` 从 gitea 服务的 cgroup 里被执行——注册恶意 unit 的动作发生在被攻陷的 web 服务进程树里。整条链：API 写入 payload，payload 触发内核本地提权漏洞，拿到 root，落盘 rootkit，注册开机自启。原报告里"入侵仅限 git 用户、root 未受影响"的结论被彻底推翻。

那么这条 rootkit 到底跑起来过没有？答案是没有，而且是侥幸。机器自八月二十七日开机后就没重启过，enabled 的 unit 等一个重启机会等了九天，等来了我的盘点。旁证也很硬：journal 里这个 unit 没有任何执行记录；攻击窗口内 audit 记录的七十三对 BPF LOAD/UNLOAD 严格配对，全部属于 systemd 自己重载 cgroup 策略；事后用 bpftool 逐个枚举，内核里三十八个 BPF 程序全部是 systemd 的设备统计和防火墙记账组件。一个带 file-read 内存补丁能力的 rootkit，离生效只差一次重启。

但这里有个更值得琢磨的问题：事件发生后我部署了一个持久化完整性巡检脚本，每小时对比 crontab、systemd unit 清单、authorized_keys 和监听端口，为什么它从来没叫过？因为基线毒化。diff 式检测只对"变化"敏感，而 am4hddh8 在巡检第一次建立基线之前就已经存在，被当成合法存量拍进了基线——从此它在检测系统眼里就是家具的一部分。这也是为什么攻击者最喜欢在得手后立刻清日志、在防守方建检测之前布局：你的检测系统上线那一刻的快照，就是它永远的盲区。修复方式是把 unit 快照从"文件名清单"升级成逐文件内容哈希，同时给巡检加了系统目录隐藏可执行文件扫描和 BPF 程序枚举两条实时检查。重建基线，自测通过。

最后是根因。提权漏洞在 Fedora 40 的 6.12 内核上被成功利用过，而这台机器的系统更新已经落后了大半年；防火墙关着，SELinux 禁着，三十个服务全在裸奔；frp 转发之后日志里所有攻击来源都是 127.0.0.1，真实 IP 从头到尾不可见。内核升级过程本身也没什么戏剧性，直连镜像卡死，走本机代理拉下来 6.14.5，重启前用 bpftool 再清点一遍内核、确认 Wi-Fi 走的是内置 iwlwifi 驱动、GPU 零负载，把一个陈年 DKMS 残留清掉，然后就等一个合适的重启窗口。

样本的 SHA256 是 `bc95ba09f62b0a4087010e7354bb0b92883ba39fbf6951d84d857ec518b18d13`，公开渠道没有任何家族匹配，是私有或定制的工具链。eBPF rootkit 在安全圈讨论了很多年，大家都说它是攻防的未来，但当你在自己家的家用服务器上真摸到一套八模块俱全、随时可以生效的东西时，那种感觉是完全不同的。它没跑起来纯属运气，而运气不是防线。如果这篇文章能让你记住一件事，那就是：定期重启不只是玄学，它能让所有"等待下一次开机"的持久化机制现出原形；以及，永远不要相信"全盘扫描确认干净"。
